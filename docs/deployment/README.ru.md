# Развёртывание

Как запустить экземпляр Vocab Bloom Hub в production: как обычные процессы Node.js (эта
страница) или в контейнерах ([`docker.md`](./docker.md) — `docker compose up` с опубликованными
образами и Postgres в комплекте). В обоих случаях впереди стоит reverse proxy с TLS.

## Что нужно для production

- **Node.js ≥ 24** и Yarn 4 (`corepack enable`) на хосте.
- **Postgres** — единственная поддерживаемая production-база; сервер отказывается стартовать с
  `NODE_ENV=production` на SQLite. Полному словарю нужны индексы, которые создают миграции
  (см. [`../performance.md`](../performance.md)).
- **TLS перед обоими приложениями** — cookie админской сессии в production помечена `secure` и
  не отправляется по обычному HTTP, поэтому админка работает только на `https://`. Прокси
  также сводит два процесса под один origin; см. [`reverse-proxy.md`](./reverse-proxy.md).

## Окружение

Оба приложения читают один `.env` в корне репозитория (или окружение процесса). Значения,
которые важны в production:

```dotenv
NODE_ENV=production
DATABASE_URL=postgres://user:password@db-host:5432/vocab_bloom
ADMIN_USERNAME=admin
ADMIN_PASSWORD=<длинный случайный секрет>
# origin, который открывает браузер; API под ним отдаёт прокси
NEXT_PUBLIC_BASE_API_URL=https://dict.example.com/api
CORS_ORIGINS=https://dict.example.com
# один reverse proxy перед сервером (см. reverse-proxy.md)
TRUST_PROXY=1
```

Значения `NEXT_PUBLIC_*` вшиваются в бандл фронтенда при сборке — их изменение означает
пересборку фронтенда. Полный список, значения по умолчанию и проверки, которые сервер
выполняет при старте, — в [`../environment.md`](../environment.md).

## Сборка и запуск

```bash
yarn install --immutable
yarn build                        # сервер → apps/server/dist, фронтенд → apps/frontend/.next (вшивает NEXT_PUBLIC_*)

yarn start                        # оба процесса в одном терминале (concurrently); останавливает оба, когда один завершился
yarn start:server                 # node apps/server/dist/src/main.js — слушает SERVER_PORT (3010)
yarn start:front                  # next start — слушает PORT (3000)
yarn site:build && yarn start:site # сайт проекта, опционально — слушает SITE_PORT (3020); docker.md#the-website
```

Окружение берётся из корневого `.env` или из файла, названного в **`ENV_FILE`** — абсолютный
путь, для чекаута, который держит секреты под `/etc`, или сборки, запущенной вне дерева
репозитория ([`../environment.md`](../environment.md)). На старте сервер пишет в лог, какой
файл загрузил, проверяет конфигурацию (завершается с кодом 1 и сообщением, когда чего-то
обязательного нет или `ENV_FILE` нельзя прочитать), применяет ожидающие миграции и логирует
выбранную базу, CORS-origins, настройку trust-proxy, пути проб, формат лога и какие
поверхности API включены. Лог идёт в stdout — JSON-строками при `NODE_ENV=production`
([`../observability.md`](../observability.md#logs)) — и его хранит менеджер процессов. Оба
процесса не держат состояния, кроме базы и, если используется, `DICTIONARY_IMPORT_DIR`.

CI запускает production-сборку тем же путём на каждый pull request — `yarn build`, `yarn start`
против Postgres, пробы и страница логина, затем SIGTERM, — так что этот путь не может
устареть незаметно (`.github/scripts/production-smoke.sh`).

## Пробы

Сервер отвечает на две пробы под `/api`, поэтому конфиги прокси маршрутизируют их как любой
другой путь API; им не нужен логин, они не ограничены rate limit, игнорируют переключатели
`PUBLIC_API_ENABLED` / `ADMIN_API_ENABLED` и никогда не кэшируются:

| Проба             | Отвечает                                                                                                                                                                                                           | Для чего                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `GET /api/health` | `200 { "status": "ok", "version": "…" }`, пока процесс обслуживает HTTP                                                                                                                                            | liveness: перезапустить процесс, когда он перестаёт отвечать                                        |
| `GET /api/ready`  | `200 { "status": "ok" }`, когда миграции прошли и база отвечает (`SELECT 1`, бюджет 2 с); иначе `503 { "status": "error", "reason": "database_unreachable" \| "shutting_down" \| "importing" \| "import_failed" }` | readiness: направлять трафик только пока ответ `200`; он становится `503` в момент начала остановки |

`503` с `database_unreachable` означает, что процесс жив, а Postgres — нет: перезапуск сервера
не поможет, поможет база. У фронтенда собственной пробы нет; эквивалентная проверка —
`GET /en/login` отвечает `200`.

## Остановка и перезапуск

Остановка — работа менеджера процессов; сервер ей содействует. По **SIGTERM** (или SIGINT)
он:

1. отвечает `503 shutting_down` на `/api/ready`, чтобы балансировщик перестал слать новые
   запросы;
2. закрывает listener — новых соединений нет — и даёт завершиться запросам в полёте;
3. закрывает пул Postgres и завершается с кодом 0.

Всё должно уложиться в **`SHUTDOWN_TIMEOUT`** секунд (30 по умолчанию). Остановка, которая
занимает дольше — идущий импорт словаря, зависшее соединение, — заканчивается записью
`forcing exit` в логе и кодом 1 вместо ожидания SIGKILL от менеджера. Дайте менеджеру таймаут
остановки _больше_ этого бюджета (`TimeoutStopSec` в systemd, `kill_timeout` в PM2), иначе он
убьёт процесс раньше.

Перезапуск — тоже работа менеджера: `Restart=always` (systemd), `autorestart` (PM2). Сервер
завершается с кодом 1, когда не может стартовать — не хватает конфигурации, недоступна база
(падают миграции), — и менеджер повторяет попытку после своей задержки; `journalctl` показывает
причину. Деплой, таким образом, — это: сделать бэкап, выложить новую сборку, перезапустить оба
процесса, дождаться `200` на `/api/ready`
([`../operations.md`](../operations.md#upgrading-the-code)). Один процесс нельзя обновить без
паузы; для нулевого простоя нужны два экземпляра сервера за прокси, по очереди выводимые из
ротации своей readiness-пробой — эта топология здесь не описана.

В целом сервер спроектирован под **один экземпляр на базу**: корзины публичного rate limit,
защита логина от повторов и ожидающие скачивания экспортов живут в памяти процесса, поэтому
реплики держали бы каждая свои. Несколько реплик за одним балансировщиком заработают, но
ослабят лимиты (каждая реплика считает отдельно) и сломают скачивание экспортов, попавшее не на
ту реплику. Сначала масштабируйте базу и прокси; общее хранилище для rate limit — изменение,
достойное issue, если реальная потребность в нескольких репликах появится.

## Менеджеры процессов

Готовые к адаптации файлы в [`examples/`](./examples/):

- **systemd** — [`vocab-bloom-hub-server.service`](./examples/vocab-bloom-hub-server.service)
  и [`vocab-bloom-hub-frontend.service`](./examples/vocab-bloom-hub-frontend.service):
  запускают `node` напрямую (без yarn посередине, чтобы сигнал и код выхода были самого
  процесса), `ENV_FILE` / `EnvironmentFile=` указывают на `/etc/vocab-bloom-hub/.env`,
  `TimeoutStopSec` больше `SHUTDOWN_TIMEOUT`, `Restart=always`. Скопируйте в
  `/etc/systemd/system/`, поправьте пути и пользователя,
  `systemctl daemon-reload && systemctl enable --now vocab-bloom-hub-server vocab-bloom-hub-frontend`.
- **PM2** — [`ecosystem.config.cjs`](./examples/ecosystem.config.cjs): оба приложения из одного
  файла, `pm2 start docs/deployment/examples/ecosystem.config.cjs` после `yarn build`, затем
  `pm2 save && pm2 startup`, чтобы подняться после перезагрузки.

Ни один из файлов не обязателен: `yarn start` под любым супервизором, который передаёт SIGTERM,
работает так же.

## Первые данные

У свежего экземпляра словарь пуст. Два способа его наполнить:

- **Самостоятельно, при первом старте** — задайте `DICTIONARY_AUTO_IMPORT=true` в `.env`
  (compose-файл так и делает; нативный запуск оставляет это выключенным): без записанной
  версии датасета сервер загружает опубликованный датасет с HuggingFace — или самый новый
  датасет из `DICTIONARY_IMPORT_DIR` — в фоне, логирует прогресс и отвечает `503 importing` на
  `/api/ready`, пока не закончит; неудачная загрузка повторяется при следующем старте
  ([`docker.md`](./docker.md#first-start-the-dictionary-loads-itself)).
- **Из админки** — войдите и запустите _Import dictionary_: с HuggingFace или из архива, когда у
  хоста нет доступа в интернет ([`../offline-import.md`](../offline-import.md)). Импорт
  несколько минут стримит прогресс; прокси не должен буферизовать этот поток (описано в
  руководстве по прокси). Одновременно идёт один импорт; второй отклоняется с `409`.

## Обновление

Сначала сделайте бэкап базы, затем заберите новую версию, `yarn install --immutable`,
пересоберите оба приложения и перезапустите процессы: ожидающие миграции выполняются на старте
сервера и привязывают базу к новой версии. Откат — это восстановление того бэкапа; полная
процедура, что бэкапить и чем обновление датасета отличается от обновления кода — в
[`../operations.md`](../operations.md).
