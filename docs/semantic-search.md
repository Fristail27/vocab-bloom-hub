# Semantic search (#655)

Storage, vector transfer, the separate semantic API, website mode and optional Docker
model service are implemented, including stale-vector filtering and validated reuse through
forks and reconciliation. Search is off by default. The integrated replay below verifies
5,000 saved meanings; full-dictionary performance verification follows separately.
Meaning vectors are never generated by the application.

## Agreed behavior

- Meaning vectors are generated **outside the application**, then imported from a file.
  There is no internal generation command, admin generation UI or re-embedding worker.
- A model is needed at request time to embed a new user's query. Its exact revision and
  input format must match those of the imported vectors.
- Semantic search has a separate API and a separate “By meaning” mode. Ordinary
  spelling search keeps its behavior; there is no automatic fallback or mixed ranking.
- `SEMANTIC_SEARCH_ENABLED` defaults to `false`. It alone controls the semantic API
  and website mode; while disabled, the application makes no query-model calls.
- The `embeddings` Compose profile starts a model service but does not enable
  semantic search. `EMBEDDINGS_URL` can instead point to a compatible remote service.
- Import/export works independently of that flag and without a running model.
  A changed meaning's stale vector must be excluded until a replacement is imported.

Model downloads are explicit operator actions; the runtime query adapter can also use an
existing Ollama service. Transfers work without the model or the optional pgvector extension.

## Dataset-local tables

`en_embedding_profiles` identifies the model and its preprocessing: model name, immutable
revision (for Ollama, record the actual model digest, not only `latest`), dimensions,
normalization, document-format version and query-format version. The profile ID is the
SHA-256 of those fields in a fixed order (`embeddingProfileId`). A profile is immutable:
change its identity when any of these inputs changes. A mutable model tag alone is not
sufficient for compatibility.

`en_meaning_embeddings` contains `(profile_id, meaning_id)`, the dimensions, SHA-256 of
the exact UTF-8 model input, and the vector. Multiple profiles can coexist while preparing
a replacement. Every read must explicitly select a compatible profile; vectors from
different profiles must never be ranked together. The composite foreign key to the profile
checks dimensions. The meaning foreign key uses `ON DELETE CASCADE`, and profile deletion
removes only its vectors. The index on `meaning_id` supports this cleanup.

The database IDs are internal links. The transfer format resolves a portable
`meaning_sync_id`, or an exact `(word, part_of_speech, sort_order)` key for datasets without
portable IDs, to the local row and validates the current input hash. It never uses
IDs from the old local prototype as portable identifiers. `embeddingVector` rejects wrong
sizes, sparse/non-finite values, float32 overflow and non-unit vectors before storage.
It rounds values to float32, as PostgreSQL and pgvector do. The current limit is 2,000
dimensions, matching pgvector's `vector` HNSW limit; the prototype uses 768.

File import validates metadata and payload through these helpers and publishes them
transactionally. Export and runtime search exclude stale inputs. A fork transfers usable
vectors separately from the ordinary table copy, validating identities, profiles and input
hashes inside the same snapshot. Reconciliation preserves compatible local vectors when it
recreates unchanged meanings, and stages incoming vectors with its durable plan.

## Portable files

A native dictionary export includes `meaning-embeddings.jsonl` when current vectors exist.
Older dictionaries without vectors remain valid. The same file can be imported on its own
with `manifest.json`, either as a directory, a ZIP, or multipart fields `embeddings` and
`manifest` at the existing admin `POST /api/en/dictionary/import/upload` endpoint. Set the
`dataset` form field to the receiving dataset. The archive upload field is `archive`.
No generation UI, command or background worker is involved.

A standalone manifest has this shape (replace the placeholders with actual hashes):

```json
{
  "version": "",
  "source": "vocab-bloom-hub",
  "files": { "meaning-embeddings.jsonl": { "lines": 1 } },
  "embeddings": {
    "format": 1,
    "profiles": [
      {
        "id": "<profile SHA-256>",
        "model": "embeddinggemma-2:latest",
        "revision": "<actual 64-character model digest>",
        "dimensions": 768,
        "normalization": "l2",
        "document_format": "meaning-v1",
        "query_format": "search-query-v1"
      }
    ]
  }
}
```

Use the source name of the target dataset. A standalone vectors import does not change
the dictionary version, content or edit history. A JSONL row identified by UUID has exactly these fields:

```json
{
  "meaning_sync_id": "<meaning UUID from the dictionary export>",
  "profile_id": "<profile SHA-256>",
  "input_hash": "<input SHA-256>",
  "embedding": [0.6, 0.8]
}
```

The two-component vector above illustrates the row shape; a 768-dimensional profile needs
exactly 768 finite numbers. Float32 rounding must leave the L2 norm within 0.001 of one.
Take `meaning_sync_id` from the meaning's `sync_id` in a normal dictionary export, which
assigns missing portable identities. Numeric database IDs and the old prototype IDs are
not accepted. For an older dataset without `sync_id`, replace `meaning_sync_id` with these
three fields (do not combine both identity forms in one row):

```json
{
  "word": "ornithologist",
  "part_of_speech": "noun",
  "sort_order": 1,
  "profile_id": "<profile SHA-256>",
  "input_hash": "<input SHA-256>",
  "embedding": [0.6, 0.8]
}
```

The importer matches the exact spelling (including case), part of speech and positive
integer `sort_order` of a base-form word in the receiving dataset. It requires exactly one
meaning before checking the hash of the complete model input, including the title and
definition. Missing or ambiguous matches and changed inputs reject the entire file; a hash
does not disambiguate duplicate keys. Reordering meanings requires preparing new keys.
This import does not assign or alter any `sync_id`. Both row forms may occur in one file,
but multiple rows for the same resolved meaning and profile are rejected, even when one
uses a UUID and another a natural key. Native exports continue to use UUIDs; a vector-only
export assigns missing meaning UUIDs too, without changing content timestamps or edit history.
The natural-key form requires an importer with this support; older importers reject it.

The profile ID is the lowercase SHA-256 of UTF-8 `JSON.stringify` of the array:
`[model, revision, dimensions, normalization, document_format, query_format]`.

`meaning-v1` hashes and embeds the exact UTF-8 string below, with no trimming, case folding
or punctuation changes. Use the headword and part of speech from the exported parent word:

```text
title: {headword} ({part_of_speech}) | text: {title}. {definition}
```

`search-query-v1` reserves the matching runtime query format:

```text
task: search result | query: {description}
```

The model name alone is insufficient: `revision` is the actual lowercase 64-character
Ollama model digest. The current importer accepts these two format versions, L2 normalization
and at most 16 distinct profiles per manifest. Each row names its own profile; dimensions
or model generations are never combined. A new input format needs an explicit implementation.

The entire file is one transaction, read in bounded batches. Unknown or ambiguous meaning
identities, mismatching current text, duplicate rows, malformed vectors, unknown profiles,
missing files or incorrect declared line counts abort the file. A partial file may intentionally
cover only some meanings; its manifest must declare that exact count. Valid rows upsert only
the named `(profile, meaning)` pairs. Other profiles and unlisted meanings are preserved.
PostgreSQL locks the input tables during import so concurrent edits cannot invalidate a
validated input before commit. Queries remain readable; content writers wait for the import.

For a full dictionary with vectors, a failed vector validation also rolls back imported
content. On a nonempty dataset the existing reconciliation workflow still applies: validated
vectors are retained in `reconciliation_embeddings` with the durable plan, then installed in
the same transaction as accepted content. Only final meanings with the same portable identity
and input hash receive them. Rejected/changed meanings, including identities remapped by
reconciliation, are skipped; no guess by title or row ID is made. Pending vectors are local
plan data and do not travel in exports. Applying a plan removes its pending vectors.

The normal export includes current vectors automatically. For a vectors-only ZIP, use
`GET /api/en/dictionary/export?dataset=<name>&embeddings_only=true`, followed by the ordinary
`export/download/<exportId>` step. An empty result reports `embeddings_empty`. Export uses the
same consistent snapshot as dictionary content. A content mismatch on import reports
`embeddings_content_mismatch`; invalid vector data reports `embeddings_invalid`, while
invalid archive/manifest packaging reports the existing `dataset_invalid`.

## Storage without the optional extension

PostgreSQL stores the payload as `real[]` (float32). SQLite uses a JSON array for storage
compatibility and tests, and does not provide semantic retrieval. The PostgreSQL migration
checks array size/shape, nulls, NaN/infinity and hash syntax. Application validation also
checks L2 normalization. SQLite enforces shape/size, hashes and foreign keys; the same
application validation is required for vector values and normalization.

The migration runs in every dataset schema, including new and staging schemas, **without
installing or requiring pgvector**. This keeps startup and vector import/export
usable when semantic search is disabled. It also avoids recording a skipped optional
migration as completed: adding the extension later does not require recreating data.

When the extension is available, pgvector can search/index the stored array by casting it
to `vector(n)`. This is an expression index, without a second copy of the payload column.
An approximate index implementation would need the same cast and profile filter, for example:

```sql
-- Example for one verified 768-dimensional profile, not automatic startup DDL.
-- Qualify vector and its operator class with the actual extension schema.
CREATE INDEX example_meaning_vectors
ON en_meaning_embeddings USING hnsw
  ((embedding::public.vector(768)) public.vector_cosine_ops)
WHERE profile_id = '<verified profile ID>';
```

`pgvectorSupport(manager)` checks the actual installed extension and its schema/version;
it performs no DDL and does not imply that the feature is enabled. Readers use the manager
of their dataset scope. The current runtime uses exact ranking; HNSW provisioning and
full-dictionary performance validation remain pending.
See [pgvector's array storage and expression-index guidance](https://github.com/pgvector/pgvector#can-i-store-vectors-with-more-precision).

## Runtime search and website mode

`SEMANTIC_SEARCH_ENABLED=true` enables a separate `GET /api/v1/search/semantic` route
and the website's “By meaning” selector. Unset/false disables them. The website reads
`GET /api/v1/search/semantic/status` from its configured API at mount time; this returns
`{ "data": { "enabled": false } }` by default, without contacting Ollama or probing vectors.
The flag is owned by the API, so an already-built website needs no separate flag/rebuild.
A restored `mode=meaning` URL while disabled shows unavailable, never lexical results.

Native server configuration (for Docker, see the next section):

```dotenv
SEMANTIC_SEARCH_ENABLED=true
EMBEDDINGS_URL=http://localhost:11434
EMBEDDINGS_MODEL=embeddinggemma-2:latest
EMBEDDINGS_REVISION=<actual lowercase 64-character Ollama digest>
EMBEDDINGS_DIMENSIONS=768
```

The URL is an HTTP(S) origin, without credentials or a path. Model, digest and dimension
must identify an imported profile with `meaning-v1` / `search-query-v1` and L2 normalization.
Missing/invalid configuration affects only semantic requests; lexical search and transfers
remain usable. No model pull or startup inference is performed. On each query the adapter
checks `/api/tags`, calls `/api/embed` with `truncate: false`, then rechecks the digest.
The response must name the requested model and contain exactly one finite, correctly sized,
unit vector. Use a model tag you keep fixed while serving queries; the before/after checks
detect normal tag updates but Ollama does not provide an atomic model-revision lease.

```text
GET /api/v1/search/semantic?query=A%20scientist%20who%20studies%20birds&dataset=wordnet&limit=10
```

`query` is trimmed and limited to 1–1,000 characters. `limit` is 1–20 (default 10).
Omitting `dataset` selects the active public dataset. Unknown or closed targets return 404
before inference. One query costs one unit of the existing shared public API rate budget.
Semantic requests are additionally capped at two concurrent requests per server process,
with no queue. Model calls share a 10-second deadline, and database statements have a
5-second timeout. The model is kept warm for 30 minutes after a request.

The response contains `{ data, meta }`. Each item has `word` (the public word projection),
`meaning` (only the matching sense, including `source` and `modified`) and `score` (cosine
similarity). `meta` contains the result count, limit, dataset terms and profile ID. Results
are ordered by score, then local meaning ID; IDs and scores belong to that one dataset.
The website shows the matching definition and attribution, with links to the exact dataset
word tab. All eight UI languages are supported, including Arabic RTL. Meaning mode selects
one dataset; grouped spelling search retains its existing behavior.

Both capability and semantic responses are `Cache-Control: no-store`. No cached result
can stand in for model/profile/visibility checks. Disabled search returns
`404 semantic_search_disabled`. Infrastructure/configuration failures use 503:
`semantic_search_unconfigured`, `semantic_storage_unavailable`, `semantic_vectors_unavailable`,
`semantic_model_unavailable`, `semantic_model_incompatible`, `semantic_search_busy` or
`semantic_search_unavailable`. Missing/currently stale vectors are an unavailable index,
not a confident “no matching meaning” answer. There is no fallback to lexical search.

The current query performs **exact pgvector cosine ranking** over the configured profile,
filtering against the current document hash before ranking. This intentionally avoids
approximate-index recall loss and stale top candidates hiding valid results. It does not
yet provision or use HNSW for production-scale retrieval. Full-dictionary latency and a
calibrated no-answer threshold remain unmeasured; the database timeout bounds expensive
scans. Scores are not confidence probabilities and results may be only loosely related.
The remaining index/performance work belongs to the integrated verification step.

The Node SDK exposes `searchSemantic({ query, dataset?, limit? })` and `semanticStatus()`;
the synchronous/asynchronous Python clients expose `search_semantic(query, dataset=..., limit=...)`
and `semantic_status()`. A cold model can exceed the SDKs' default 10-second timeout; callers
can raise their existing request timeout. Tests use an isolated local HTTP fixture model,
not a running Ollama installation or the developer's database.

## Edits, reverts, forks and merges

Validity is computed from the current complete model input, not an editorial flag or a
background job. Changes to the headword, part of speech, meaning title or definition make
the old input hash mismatch. Both semantic search and vector export exclude that vector
immediately after the content transaction commits. Edits through accepted suggestions and
reverts use the same rule. Examples, translations, pronunciation, attribution and other
fields outside `meaning-v1` do not invalidate it.

An ordinary edit leaves the old derived row stored. An exact revert can reuse it if the
same meaning row and matching vector still exist. Deleting a meaning cascades to its
vectors; restoring deleted text does not recreate them. No vector changes create content
history, and no operation contacts the model to regenerate dictionary vectors.

A dataset fork captures content and vectors in one PostgreSQL `REPEATABLE READ` transaction.
It transfers supported profiles in bounded batches and resolves `meaning_sync_id` in the
receiving content; equal numeric IDs alone are never proof of compatibility. Stale vectors
and unknown preprocessing/profile identities are omitted. Each model generation remains
separate. A successful fork has independent vector rows: removing its parent has no effect.
The same transaction publishes the schema and registry; failure leaves no partial fork.

Reconciliation can rebuild nested meaning rows even for an unrelated word edit. It retains
current local vectors for that word before rewriting and restores only those whose portable
identity and exact input remain unchanged afterwards, using the new local row IDs. Changed,
deleted or remapped identities receive no guessed replacement. The retained data is scoped
to one word at a time; the entire dictionary is not buffered in memory.

Source imports and parent/related merges snapshot incoming current vectors with the plan.
Changing or deleting source vectors after preparation does not change the saved plan.
Publication validates the final identities/hashes under the content transaction's write locks.
Keeping local content or choosing custom text never attaches a vector for rejected incoming
text. A matching incoming vector can replace the same profile's local value; other profiles
remain separate. A publication failure rolls content and vectors back together.
Applying or cancelling a plan removes its pending vector payloads; cancellation leaves
live content and live vectors intact.

Native exports/imports retain portable identities and profile metadata, including after a
fork. Unsupported stored profile formats are omitted from reuse/export; incoming files
still undergo strict validation. Runtime search requires the exact configured profile, even
if another generation has identical dimensions. With no current vectors for that profile,
it reports unavailable and does not use another model's vectors. Full replacement vectors
are prepared externally and imported using the file workflow above.

## Docker and remote Ollama

Two independent settings:

| Configuration                             | Model container               | Meaning search                                                   |
| ----------------------------------------- | ----------------------------- | ---------------------------------------------------------------- |
| No `embeddings` profile, flag unset/false | Not started                   | Disabled                                                         |
| `embeddings` profile, flag unset/false    | Started                       | Disabled                                                         |
| No `embeddings` profile, flag true        | Not started; use a remote URL | Enabled; 503 if unavailable                                      |
| `embeddings` profile, flag true           | Started                       | Enabled; 503 until compatible model, extension and vectors exist |

For the bundled service, edit the instance's `.env`:

```dotenv
COMPOSE_PROFILES=db,site,embeddings
SEMANTIC_SEARCH_ENABLED=false
EMBEDDINGS_MODEL=embeddinggemma-2:latest
EMBEDDINGS_DIMENSIONS=768
# Default inside Compose; omit the variable or use this address:
EMBEDDINGS_URL=http://embeddings:11434
```

Start it and **explicitly download** the chosen model:

```bash
docker compose up -d embeddings
docker compose exec embeddings sh -c 'ollama pull "$EMBEDDINGS_MODEL"'
docker compose ps embeddings
# Read the full digest through Node in a one-off API container (no API/DB startup):
docker compose run --rm --no-deps --entrypoint node server -e 'fetch(process.env.EMBEDDINGS_URL + "/api/tags").then(r => r.json()).then(console.log)'
```

Copy the full `digest` of the matching model from `/api/tags` into `EMBEDDINGS_REVISION`.
It must match the imported profile exactly; changing a mutable tag or merely copying a new
digest does not convert old vectors. Import externally prepared compatible vectors before
setting `SEMANTIC_SEARCH_ENABLED=true`, then recreate the server with `docker compose up -d server`.
Keep the flag false while preparing data. No application command prepares dictionary vectors.

The official `ollama/ollama:0.40.8` runtime is pinned separately from the model; override it
with `EMBEDDINGS_IMAGE` when deliberately upgrading. The named `embeddings-data` volume holds
models at `/root/.ollama` and survives container recreation and `docker compose down`.
`down --volumes` deletes this volume **and the database volume**. The service publishes no
host port. The API talks to it over the Compose network; browsers talk only to the API.

The healthcheck runs `ollama show` for `EMBEDDINGS_MODEL`: it checks the daemon and presence
of that model, without inference or downloads. A new empty volume is **unhealthy until the
explicit pull succeeds**. Start with `up -d`, provision the model, then use `up -d --wait`
if desired. A healthy container does not promise a matching digest, valid vectors or working
inference; the semantic API checks those on every query. The server has no dependency on
this service, so unavailable inference does not prevent startup, readiness, lexical search
or vector import/export. Models are never pulled automatically. When semantic search is
enabled, API startup attempts to activate pgvector as described below.

The bundled service explicitly forces CPU execution and system RAM with
`CUDA_VISIBLE_DEVICES=-1`, `ROCR_VISIBLE_DEVICES=-1` and `OLLAMA_VULKAN=0`. These values
belong to the `embeddings` service's environment and do not inherit GPU selection from
the instance's `.env`. They affect inference, not the size of the downloaded image.
For an optional NVIDIA GPU on a configured Docker host, an override must both expose
the device and re-enable CUDA selection, for example:

```yaml
services:
  embeddings:
    gpus: all
    environment:
      CUDA_VISIBLE_DEVICES: '0'
```

Other GPU runtimes need their own device settings and corresponding environment overrides;
follow the [official Ollama Docker instructions](https://docs.ollama.com/docker) and
[GPU selection documentation](https://docs.ollama.com/gpu).
On Docker Desktop for macOS, use native Ollama and `host.docker.internal` if you need Metal
acceleration rather than Linux-container CPU inference.

For Ollama already running on another machine, omit `embeddings` from `COMPOSE_PROFILES`:

```dotenv
COMPOSE_PROFILES=db,site
EMBEDDINGS_URL=http://192.168.0.106:11434
EMBEDDINGS_MODEL=embeddinggemma-2:latest
EMBEDDINGS_REVISION=<the full digest matching the imported vectors>
EMBEDDINGS_DIMENSIONS=768
SEMANTIC_SEARCH_ENABLED=true
```

The URL must be reachable **from the API container**. `localhost` inside that container is
the API itself, not the host or the Windows machine. `host.docker.internal` names the Docker
Desktop host; use the LAN address for another machine. Only query text and its fixed prompt
are sent to this configured service, not dictionary content. An offline machine produces
an explicit semantic 503; ordinary search remains available. To disable the feature, set
the flag false and recreate the server; the model profile and stored vectors can remain.

### PostgreSQL extension and existing data

`vocab-bloom-hub-postgres` builds on the same `postgres:17-alpine` family as the previous
bundled database, retaining `/var/lib/postgresql/data` and `postgres-data`. It adds pgvector
0.8.1 from a checksum-verified source archive, compiled without host-specific CPU flags.
The extension files are available, but starting the database image alone does not activate
them. With `SEMANTIC_SEARCH_ENABLED=true`, API startup automatically runs
`CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA public` before dictionary migrations.
This works for a fresh database and an existing volume; no manual SQL is normally needed
with the bundled database credentials. Concurrent API starts serialize activation. Existing
extensions keep their version and schema; startup never runs `ALTER EXTENSION UPDATE`.

When the flag is false/unset, startup makes no attempt to activate pgvector. If activation
fails because the package or database privileges are missing, its transaction is rolled back
and a warning is logged; ordinary startup and lexical reads continue. An administrator can
then enable it manually:

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -c "CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA public;"'
```

The dataset schemas share that extension. Existing extensions in another schema are supported.
For external PostgreSQL, have its administrator install the matching server package and,
if the application user cannot create extensions, run the same SQL in the target database; see the
[pgvector installation guide](https://github.com/pgvector/pgvector#installation).
Without it, storage/transfers and lexical search still work; enabled semantic search returns
`semantic_storage_unavailable`. SQLite does not provide semantic retrieval.

Before upgrading an existing installation, take and verify a backup using the normal
[database backup procedure](./database.md#backups), then stop the application writers,
replace the PostgreSQL image and restart the apps. Keep the existing volume; do not use
`down --volumes`. This is an Alpine PostgreSQL 17 image update, **not** a major-version or
Alpine-to-Debian migration. A different PostgreSQL major or operating-system family requires
a separate tested upgrade/dump-and-restore plan, not mounting the old volume directly.
Preserve a backup of the old image/version configuration too. If disabling semantic search,
keep the extension-capable database image; removing its binary files while the extension is
still installed is not a rollback procedure.

Before these images are published, build this checkout with `docker-compose.build.yml`.
Use the Compose file from the same release as `VBH_TAG`; old application releases do not
have the new PostgreSQL image tag.

## Integrated prototype replay (2026-10-23)

The opt-in `test/semantic-prototype.pg-spec.ts` replays the locally saved prototype through
real multipart import, the public semantic API, ZIP export and archive reimport. It creates
and drops a new database, assigns fresh portable identities to fixture meanings, and opens
the saved vector cache read-only. It does not generate embeddings or contact Ollama.
Dictionary text and vectors remain in the ignored `imports/` directory, not in the repository.
The source is an older local snapshot; this is not a production dataset installation.

Use Node 24.9+ and a **disposable** PostgreSQL instance with pgvector available and database
creation privileges. From the repository root, with the saved prototype present:

```bash
DATABASE_URL=postgres://... TEST_PGVECTOR=true \
  SEMANTIC_PROTOTYPE_DIR="$PWD/imports/semantic-prototype-2026-10-22" \
  yarn workspace server test:postgres semantic-prototype.pg-spec.ts
```

Without `SEMANTIC_PROTOTYPE_DIR`, this private-data test is skipped. CI uses the committed
synthetic storage, API, transfer and lifecycle fixtures instead. The replay writes
`step7-api-report.json` alongside the saved prototype, containing per-query timings and
seed ranks. Required inputs are `COMPLETE.json`, `model.json`, `meanings.jsonl`,
`rankings.jsonl` and `cache.sqlite`; these are local prototype artifacts, not an alternative
application import format. The test constructs the documented portable transfer files.

### Results and limits

Measured on Apple M4 Pro / macOS arm64, Node 24.10.0, Docker PostgreSQL 17.11 Alpine arm64
and pgvector 0.8.1. The corpus contains 5,000 meanings with 768-dimensional float32 vectors.
There are five warmup requests followed by one sequential pass of 132 saved queries,
requesting ten results. Timings include the Nest API, local HTTP model adapter, database
ranking and response projection. The HTTP fixture returns cached query vectors: **actual
model inference, model RAM/VRAM and LAN latency are not measured**. This is an exact scan
without an ANN index, not a concurrency or full-dictionary capacity test.

| Operation / storage                                          |       Measured result |
| ------------------------------------------------------------ | --------------------: |
| Semantic API, median / p95 / maximum                         | 60.4 / 64.0 / 70.5 ms |
| Multipart vector import                                      |                7.42 s |
| Vector ZIP export and download                               |                5.59 s |
| ZIP reimport after replacing numeric IDs                     |                7.91 s |
| Raw float32 vector payload                                   |             14.65 MiB |
| Vector table including indexes and TOAST, after first import |             21.33 MiB |
| Entire disposable fixture database, after first import       |             35.73 MiB |

Storage sizes are disk allocation, not RAM requirements. The report also records sizes
after delete/reimport; unreclaimed tuples can increase those allocations before vacuum.
These small-corpus measurements do not establish full-dictionary storage or latency.

Every query's top ten meaning identities matched the saved offline ranking, with score
agreement to five decimal places. Import/export also passed with semantic search disabled
and the model stopped. After changing every numeric meaning ID, reimport restored all
5,000 vectors with identical profile, portable identity, input hash and float32 payload.

| Saved query category                   | Queries | Seed meaning first | Seed meaning in first five |
| -------------------------------------- | ------: | -----------------: | -------------------------: |
| English descriptions                   |      60 |         50 (83.3%) |                         60 |
| Russian descriptions                   |      60 |         46 (76.7%) |                         60 |
| Out-of-scope requests, English/Russian |      12 |     Not applicable |             Not applicable |

These are assistant-authored seed labels on a corpus deliberately containing the expected
answers, not independent human judgments. The already-inspected evaluation subset scores
17/20 English and 16/20 Russian at rank one; all forty seed meanings appear in the first
five. Errors include related concepts, the wrong sense/POS, reversed roles and antonyms.
The twelve out-of-scope requests still produce nearest candidates: **there is no calibrated
no-answer cutoff**. Their top scores (0.569–0.682) overlap with positive-query top scores
(0.658–0.863). Similarity is not a probability that an answer is correct. Broader independent
relevance evaluation, full-dictionary latency and ANN indexing remain separate work.

### Browser and deployment verification

The semantic mode, disabled/restored URLs, explicit failure without lexical fallback,
selected datasets and mobile Arabic RTL pass the real Chromium suites:
